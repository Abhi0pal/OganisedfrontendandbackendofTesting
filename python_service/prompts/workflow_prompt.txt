## PROCESSING RULES (STRICT)

### 1. Workflow Mapping

* workflow.workflowCode → workflow_definition.code
* contextDetails.formName → name
* description → derive from purpose
* version → always 1
* status → always "PUBLISHED"

---

### 2. Step → Process Mapping

* Each step → one process
* stepOrder = index + 1
* processId → processCode
* processName → name (remove suffix like "(Forward)", "(Revert)")

---

### 3. Node Type Rules

* First step → "START"
* Last step → "END"
* Others → "STANDARD"

---

### 4. Assignee Rules

* assigneeType → "ROLE" for ALL nodes
* START:

  * MUST include roleName
* STANDARD:

  * MUST include roleName
* END:

  * MUST NOT include roleName

---

### 5. Action Transformation

Each action MUST follow:

```json id="action-template"
{
  "actionCode": "FORWARD | APPROVE | REJECT | REVERT | QUERY",
  "actionLabel": "string",
  "displayOrder": number,
  "transitions": []
}
```

Rules:

* actionCode must be uppercase
* displayOrder starts from 0
* Map:

  * Submission → FORWARD
  * Forward → FORWARD
  * Approve → APPROVE
  * Reject → REJECT
  * Revert → REVERT
  * Query → QUERY

---

### 6. Transition Mapping (CRITICAL)

Each action MUST include:

```json id="transition-template"
{
  "targetProcessCode": "P_xxx",
  "label": "string",
  "priority": 0
}
```

Mapping:

* nextStepProcessId → targetProcessCode
* Must match an existing process

---

### 7. Terminal Action Rules

* APPROVE and REJECT → must go to END node
* If Next Step Role = "END", route to END node
* END node must have:

```json id="end-actions"
"actions": []
```

---

### 8. Revert / Query Rules

* REVERT → follow nextStepProcessId mapping (not always previous step)
* QUERY → step 1 (Applicant/Citizen)

---

### 9. SLA Rules

* Use slaHours if present (store internally if not in schema)

---

### 10. Conditions Handling

* Convert conditions into assignment_rule_json internally
* Do NOT ignore

---

### 11. Alerts Handling

* Ignore alertsAndNotifications in output

---

### 12. Form Type Rules

* `formTypeId` MUST be **2** for ALL STANDARD (department/officer) nodes.
* START node (Investor/Citizen): do NOT set formTypeId (omit or null).
* END node: do NOT set formTypeId (omit or null).

```json id="formtype"
"formTypeId": 2
```

---

### 13. Position Rules (STRICT UI GRID)

* Step 1 → (100, 200)
* Step 2 → (450, 200)
* Step 3 → (800, 200)
* Continue increment X by 350

---

### 14. Validation Rules (STRICT)

DO NOT generate output if:

* Missing transitions
* Invalid process references
* Duplicate processCode
* Empty actions (except END)
* Missing roleName in START or STANDARD

---

### 15. Structural Integrity

* Only ONE START node
* Only ONE END node
* No orphan steps
* All steps must be connected

---

### 16. Naming Rules

* processCode → "P_001", "P_002", ...
* actionCode → FORWARD, APPROVE, REJECT, REVERT, QUERY

---

### 17. Start Node Rule

* Must contain ONLY forward-type action

---

### 18. End Node Rule

* Must contain:

```json id="endnode"
"actions": []
```

---

## FINAL INSTRUCTION

Convert the given SRS JSON into a valid workflow_definition JSON strictly following all rules and the PROCESS TEMPLATE.

Output ONLY JSON. No explanation.
